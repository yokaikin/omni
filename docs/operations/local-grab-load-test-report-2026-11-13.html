压测概况

环境与数据

  • 运行环境：本机开发环境，Docker Compose 微服务栈
  • 入口：http://localhost:8088 Gateway
  • 场次 / 票档：910062 / 920186
  • 压测前 PostgreSQL 余票：84 张
  • 用户：100 个不同的本地演示用户

请求流程

  1. 并发准备用户身份并创建观演人。
  2. 并发调用 POST /api/grab/requests，每人请求 1 张。
  3. 轮询抢票进度直到订单创建、售罄、限购、失败或超时。
  4. 通过正常取消订单接口回收待支付订单，并删除本轮观演人。

执行脚本：scripts/load-test-grab.mjs。脚本仅允许本机 HTTP Gateway，且要求显式设置确认变量。

前置试跑与异常

前置试跑未通过清理 最初的 2 用户真实 HTTP 冒烟中，两个抢票请求都成功创建订单；清理时订单服务通过支付宝占位配置同步支付状态失败，正常取消接口拒绝释放这两笔待支付订单，余票从 84 降至 82。

之后为本机开发环境启用受控的支付 mock 清理路径，先确认环境和库存恢复，再进行正式 100 并发压测。正式压测中的 82 笔订单均通过正常取消接口回收，100 个观演人也全部删除。

该前置问题属于测试环境清理路径，不计入正式 100 并发的提交失败数。

压测发现并修复的问题

已修复 取消订单后抢票 Redis 锁未即时释放

压测清理后 PostgreSQL 库存已恢复，但抢票 Redis 中仍残留本轮 82 个用户锁，可见库存为 0；后续查询库存才触发与票务库同步。

修复后，订单取消成功会在事务提交后发布 ORDER_CANCEL 事件。抢票服务按订单、场次、票档匹配抢票请求，释放用户 admission/hold，恢复 Redis 库存并同步票务库存。

已修复 订单服务健康检查返回 500

压测期间业务请求仍成功，但 /actuator/health 返回 500，日志显示 Sentinel 缺少 TransportConfig。

重建并重启订单服务镜像后，确认包含 sentinel-transport-common-1.8.6.jar；当前 127.0.0.1:8083/actuator/health 返回 {"status":"UP"}。

结论与适用范围

结论：本机开发环境下，100 个并发用户的真实 HTTP 抢票流程没有出现请求提交失败、轮询超时、服务崩溃或超卖；售罄和限购结果正常返回。压测发现的取消后 Redis 锁/库存同步问题及订单健康探针问题均已完成代码修复和自动化验证。

本结果用于本机毕设验收，不能推导生产最大并发、峰值吞吐或公网部署容量。修复后已经通过单元测试、构建和运行态健康检查，但没有在共享开发库再次执行完整 100 并发；完整的修复后业务取消冒烟仍待隔离测试数据环境执行。

本次未执行真实支付宝支付、短信发送或公网业务测试；支付流程不属于这次抢票并发压测负载。
